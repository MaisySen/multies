# Mobile app

The Multies phone app is an Expo (React Native) project for iPhone and Android
([adr/0004](adr/0004-expo-mobile.md)). It lives in its own folder, `mobile/` in the GitHub repository
(a separate local checkout during development), with its own `package.json`, lint and Jest tests. It
uses the same REST API as the web app (cookie session kept by the app) and the shared brand tokens.

## Build

```bash
cd mobile
npm ci
npx jest                     # unit tests
npx tsc --noEmit && npx eslint .
export ANDROID_HOME=$HOME/Android/Sdk
npx expo prebuild --platform android --clean --no-install
cd android
./gradlew assembleRelease -PreactNativeArchitectures=arm64-v8a -PmymailRequireUploadKey=true --no-daemon
./gradlew bundleRelease -PreactNativeArchitectures=arm64-v8a,armeabi-v7a,x86_64 -PmymailRequireUploadKey=true --no-daemon
```

The APK is for direct installs on modern phones; the AAB is for Google Play. Full detail, including iOS,
is in the mobile project's `docs/release.md` and `store/SUBMISSION.md`.

## Signing

- `android/` is generated by `expo prebuild`; the config plugin `plugins/with-release-signing.js` adds the release signing block on every prebuild.
- The upload keystore and its passwords are kept outside the repo. Where they are and how to use them: "CREDENTIALS (owner email v7)", Android upload keystore section. The owner keeps a backup copy.
- `*.jks`, `*.keystore`, `credentials.json` and `secrets/` are git ignored. Without the signing values a release build fails when `-PmymailRequireUploadKey=true` is set.
- Google Play app signing holds the app signing key; the upload key only signs uploads.

## Versioning

- `expo.version` in `app.json` is the user facing version (semver). `android.versionCode` and `ios.buildNumber` go up by one for every store upload, never reused.
- Bump both in one commit, for example `chore(mobile): 1.6.0 (versionCode 7)`.
- The app must keep working with the production API it was built against: API changes are additive.

## Store steps

1. Build and sign the AAB and APK as above; check them with `bundletool validate` and `apksigner verify`.
2. Smoke test the APK on a phone or emulator against production: sign in, mail, chat, tasks, notifications.
3. Google Play Console: upload the AAB to internal testing, then promote to production with release notes.
4. App Store: archive in Xcode, upload to App Store Connect, TestFlight, then submit for review with the fixed App Review demo login.
5. Store listings point at https://multies.si/support and https://multies.si/delete-account.
6. Note the release in the CHANGELOG.

## Sign in

The app has no password screen. "Continue with Multies" and "Create account" open the Multies sign in
page (the identity provider's Universal Login) in the system browser as the Native application
"Multies Mobile", with PKCE, state and nonce, and the callback `mymail://auth/callback` (the app.json
scheme). The app swaps the code for an ID token, sends it to `POST /api/auth/mobile/exchange`, and keeps
only the Multies session cookie in SecureStore. Details: [auth.md](auth.md). Builds can point at another
tenant with `EXPO_PUBLIC_IDP_DOMAIN` and `EXPO_PUBLIC_IDP_CLIENT_ID`.
