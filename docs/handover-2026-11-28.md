### Integration steps before the next traffic switch

1. Apply the change on a dedicated branch off `main` or the reconciled source. Run
   `tests/worker-release-guard.test.ts` and a full type check.
2. Build and seal the deployable package together: `RELEASE=<reviewed-release> npm run build:release`.
   Never replace `dist/worker/assets` with a standalone Vite build.
3. Carry the previous live immutable assets alongside the new set and verify continuity:
   `npm run verify:worker -- --release <reviewed-release> --previous <known-good-worker-release.json>`.
4. Keep the seal in the same CI artifact. Never regenerate it at promotion. Never upload the seal,
   `dist/web/index.html` or browser source maps to public assets.
5. Switch production traffic in two stages: first a compatibility bridge (last known-good Worker code
   with the union of old and new assets), verify the edge has converged, then move traffic to the
   verified new Worker while keeping both asset sets.
6. Run real fresh-session browser checks, not only HTTP 200 probes, before declaring the rollout
   complete.

## 10. Backups and readiness for the next migration

Standard gate: verify a fresh encrypted off-peak backup and an isolated restore before the next
production migration.

### Off-peak window

Database exports and production migrations run only between 21:00 and 07:00 AEDT (Australia/Sydney).

### Checklist before the next production migration

1. Run one fresh off-peak export of the production database with the dedicated backup credentials,
   encrypt it, store it in the private backup storage and remove the local plaintext.
2. Independently retrieve the stored archive, verify its SHA-256 and decryption, and restore it in
   isolation: `PRAGMA integrity_check`, `PRAGMA foreign_key_check`, schema parity, all 162 applied
   migrations (including `0171_operator_access_audit` and `0172` to `0178`), and the owner and audit
   rows.
3. Confirm no earlier export is still in progress, so exports do not collide or double count row
   reads.
4. Capture a fresh D1 Time Travel bookmark immediately before the migration. Do not restore the
   database automatically.
5. Rehearse the migration on a disposable hosted D1 database or a restored snapshot first, and gate
   any Worker deploy behind the release guard (`build:release`, asset carry,
   `verify:worker --previous`) with a two-stage switch.

See [runbooks/db-backup-restore.md](runbooks/db-backup-restore.md) for the commands.
